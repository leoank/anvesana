`\_SB.NPCF` (NVDA0820, `_STA` 0x0F on Linux) `_DSM`, GUID 36b49710-2483-11e7-9598-0800200c9a66:

- Answers only revision 0x0300 (`If (ToInteger (Arg1) != 0x0300) Return (0x80000001)`), no
  `_OSI` test.
- Function 0 (supported functions): `Unicode ("?")`, bytes 3F 00: functions 0-5.
- Function 1: a constant 0x880-byte (2,176) buffer with no visible structure (no version or
  size header in the clear): the static table, opaque.
- Function 2: a constant 10-byte buffer.
- Function 3: a 0x87-byte table with four dwords filled at call time from EC register pairs
  0x260/0x261 ... 0x266/0x267 (`KEL2`); most likely the power limits, which would follow the MSI
  mode.
- Function 4: parses a list of (id, length, value) entries and, for id 0x3000, writes EC
  register 0x26A (`ECWB`): the driver's way to tell the EC something.
- Function 5: returns 0.

`nvidia-powerd` 2.0 (from the driver package, started as a transient unit as NixOS's
`hardware.nvidia.dynamicBoost` would) quit at once: "ERROR! SBIOS support not found for NVPCF
GET_SUPPORTED function" (and `dmidecode` missing, incidental). The open kernel driver 615.78.08
sends NVPCF revisions 0x100 and 0x200 only (`acpidsmguids.h`: `NVPCF_ACPI_DSM_REVISION_ID`,
`NVPCF_2X_ACPI_DSM_REVISION_ID`; `os.c` picks one per function), and its `nvpcf.h` defines
tables up to 2.x. So on Linux the driver gets 0x80000001 for everything and Dynamic Boost has no
channel to this firmware; Windows' driver 621.01 evidently speaks NVPCF 3.x.

For H1 of [[EXP-20261104-ssfn9a]]: the platform data is not plain ACPI data. Function 1 is an
opaque blob, which fits "encrypted"; function 3's live values come from the EC in the clear.
The tables copied for this run stay out of git (`tables/`, ignored).
