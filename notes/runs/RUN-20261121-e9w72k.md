## Notes

Done 2026-11-21 13:02-13:33 on curiosity (curiosity ISO, kernel 7.0.14-1022-nvidia, stock open
driver 620.70.06, no nvidia-powerd; BIOS G2621NMS.10B, AC), by hand: Ank started the sampler
as root, I ran the rest. `run.sh` is the same steps as one script. Prompted by
NVIDIA/open-gpu-kernel-modules#1521, where HP OmniBook X 14 owners found that the GPU follows
a SoC long-term power limit (PL1) in a page at physical 0x1C238000 named in HP's DSDT, and
that it slides from 80 to 45 W under load.

This firmware's ACPI tables do not name that page (no 0x1C23xxxx region, no `_PL1`/`EPL1`
fields), and it is not in `/proc/iomem`. Read-only through `/dev/mem` (`budget.py`, HP's
offsets) it holds the same layout here: PL1 80 W, PL2 95 W, SPL1-4 134/137/140/150 W, SoC
power (`EPL1`, ~8 s average) 4 W at idle, SoC and GPU temperature 44 °C, and at +0x604 a
value that follows the GPU's power (76.8 W at idle).

cuBLASLt alone, 120 s per data type, medians over the last five minutes of load:

| | balanced (EPP 127) | power-saver (EPP 255) | Windows (baseline) |
|---|---|---|---|
| PL1 | 80 W, constant | 80 W, constant | not read |
| SoC power (`EPL1`) | 77.1 W | 77.7 W | |
| +0x604 (GPU budget) | 49.9 W | 57.8 W | |
| GPU power, bench average per type | 46.9-56.6 W | 53.3-63.8 W | 61.3 W (whole cuBLASLt phase) |
| SoC temperature | 96.4 °C | 89.7 °C | |
| fp32 / tf32 TFLOPS | 13.37 / 43.84 | 13.88 / 45.13 | 14.63 / 47.29 |
| fp16 / bf16 | 75.22 / 74.80 | 79.03 / 78.32 | 85.63 / 86.34 |
| fp8 / nvfp4 | 151.60 / 283.71 | 157.34 / 294.22 | 170.20 / 330.70 |

So unlike the HP, PL1 does not move here. The SoC runs on it (77-80 W) under a GPU load, and
the GPU gets what the rest of the SoC leaves: the GPU budget value and the GPU's power track
each other, with clock event reason 0x4 (SW power cap) throughout. The CPU side, at the
balanced profile's energy preference 127, takes about 27 W while the CPU has nothing to do
beyond feeding the GPU; at 255 it takes about 20 W, and the GPU gets about 8 W more and runs
3-5 % faster, at a lower SoC temperature. Earlier Linux runs showed the CPU averaging 3.4 GHz
during cuBLASLt against 1.66 GHz on Windows (RUN-20261118-g2tm8p, `bench compare`).

This also explains why NVIDIA's Dynamic Boost matters on this machine: shifting the shared
SoC budget from CPU to GPU is its job. What is left to Windows' ~61 W (power-saver here gives
~58 W) is not established; Windows' PL1 was not read. The benchmark tags and profile names
are in `run.log`; the first sampler (13:02-13:17) covered a failed attempt (the bench's
TensorRT wheel download was cut off) and is not used.

**With n1x-gpu-boost** (14:26-14:33, `gpu-boost/`; the daemon from `nix/n1x-gpu-boost.py`
started by hand as root, profile balanced). It switched EPP 127 -> 255 when the GPU reached
96 % and back to 127 when it went idle (`gpu-boost.log`), once each. Over the last five minutes
of load: PL1 80 W, SoC 77.6 W, GPU budget 58.2 W, SoC 89.9 °C, the same as power-saver. GPU
power 55.3-63.9 W per type. TFLOPS: fp32 13.52, tf32 44.28, fp16 72.92, bf16 76.31, fp8 151.23,
nvfp4 292.33; between balanced and power-saver for most types and below both for fp16. Across
the Linux runs so far fp16 has ranged 69.95-79.03 TFLOPS at the same settings, so the GPU's power
share is the measure to trust here, not a single run's throughput. A CPU benchmark was not
run: the daemon only acts on GPU utilization, and it stayed at 127 outside the GPU load.

## Reproduce

sudo for the sampler. It cannot control temperatures, the fan, or the firmware's budget
policy.
