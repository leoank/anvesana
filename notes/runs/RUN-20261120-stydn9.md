## Notes

Done 2026-11-20 23:31-23:40 on curiosity (curiosity ISO from neusis, kernel 7.0.14-1022-nvidia,
stock open driver 620.70.06 without the NVPCF patch, no nvidia-powerd; BIOS G2621NMS.10B, on AC,
power profile performance). Ank set MSI Center's top performance mode on Windows and rebooted
straight into Linux; the run was the first GPU load of that boot. The write-free test proposed in
[[RUN-20261120-g7hznd]]: does the mode that gives ~61 W on Windows carry over to Linux?

It does not show. cuBLASLt alone averaged 52.1 W (peak 64.7 W, SM 1,942 MHz, GPU peak 82 °C),
against 51.9 W in [[RUN-20261118-g2tm8p]] and 61.3 W on Windows. `nvidia-smi` sampled every
0.5 s (`smi.csv`): of 366 samples above 30 W, 312 had only the SW power cap as the clock
event reason (0x4), none a thermal or HW slowdown; mean 52.8 W. The GEMMs came out 2-7 %
below the earlier Linux run (fp32 12.95, tf32 41.51, fp16 69.95, bf16 74.04, fp8 148.97,
nvfp4 277.78 TFLOPS; `compare.md`), within the spread of a warm, single-benchmark run.

Two readings stay open: MSI Center's mode is not kept across a reboot (MSI Center may apply it
at each Windows login rather than store it in the EC), or the mode is not what sets the cap and
the extra ~10 W on Windows is Dynamic Boost through NPCF. This run cannot tell them apart. The
mode was not read back on Linux: there is no interface to MSI's firmware service here.

## Reproduce
Run `script` from the repo root as the desktop user on a booted curiosity, after setting MSI
Center's top mode on Windows and rebooting into Linux. It cannot control the firmware's state
carried from Windows, the temperatures, or the power source.
