## Notes

`sudo n1x-hub-test` on bbaum-pc-7, ISO e70db851 (spi-hid-acpi evaluates `_RST` itself),
standby-notify entry, boot 72000af6, 2026-11-10 23:31 (run by Ank). Output on SPARKDATA under
`bootlogs/bbaum-pc-7/hub-test-20261110_233148/`.

- `ACPI: \_SB_.SENH: anvesana: _RST evaluated` on every probe, and now the hub answers:
  IRQ 232 counted 6 (trial A) and 9 (trial B), all on CPU 0. H2 holds: the missing `_RST` was
  why the hub never interrupted. (EINT 190's status bit was still never caught set: the
  handler acks it within microseconds, faster than the 20 ms sampling.)
- About 45 ms after `_RST` the driver read a valid header, `03 e7 42 5a` (version 3, length
  0x2e7 words = 2972 bytes, last fragment, sync 0x5A), and rejected it: "Input report body
  size 2972 > max expected of 2048". So the reset response and the device descriptor went
  through silently, the driver asked for the report descriptor, and the 2972-byte answer
  failed the core's check against the device descriptor's `max_input_length` (2048). The probe
  then timed out ("Expected report descriptor not received: -110", "Failed to add hid
  device"). The interrupt order (A or B) makes no difference.

Fix for the next run (`nix/spi-hid/spi-hid-core.c`, marked anvesana): bound a body by the
larger of `max_input_length` and what the buffer holds; `spi_hid_ll_parse()` already grows
the buffers to the report descriptor's length before asking for it.

## Reproduce
On the laptop, booted from ISO e70db851: `sudo n1x-hub-test`. Not controlled: the
coprocessor's state since boot.
