## Notes

`sudo n1x-hub-test` on bbaum-pc-7, live image ISO 0459ccac, standby-notify entry, boot
9d8ff26b, 2026-11-10 23:01 (run by Ank). Output on SPARKDATA under
`bootlogs/bbaum-pc-7/hub-test-20261110_230120/`.

- Both orders (A: reset then IRQ; B: IRQ then reset): IRQ 232 stayed at 0 on every CPU (the
  summary's "irq count 190" is a bug in this version of the script, which added the "190"
  of "mt-eint 190" to the counts; fixed afterwards). EINT 190's status bit never set (146 and
  147 samples over 3 s); after bind it was unmasked (mask 0), edge (sens 0), falling (pol 0),
  domain enabled.
- The one-shot poll 1.5 s after reset read headers `00 00 00 00` (A) and `d8 d8 d8 d8` (B),
  neither a valid HID-over-SPI header (sync byte 0x5A); the reset stayed pending.

So H1 (an edge lost before enable_irq) is false: the hub sends no reset response at all.

Found afterwards, reading the code: the reset was never sent. `spi_hid_acpi_deassert_reset()`
calls `device_reset(&adev->dev)`, but an `acpi_device`'s own struct device has no fwnode
(`acpi_init_device_object()` does not set it), so `ACPI_HANDLE()` is NULL, `__device_reset()`
skips `_RST` and fails looking for a reset controller, and `spi_hid_dev_init()` ignores the
error. `_RST` (SENH: write 1 to 0x1AB20008, the coprocessor doorbell) has never run on Linux.
Fixed in `nix/spi-hid/spi-hid-acpi.c` (evaluate `_RST` on the handle) for the next run.
